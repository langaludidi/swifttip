## Completed in this pass

### Public API failure semantics

Customer Tip and quote APIs now use a shared bounded JSON reader and failure classifier.

- Default public JSON body ceiling: 16 KiB.
- Malformed/empty JSON: HTTP 400.
- Oversized body: HTTP 413.
- Unsupported content type: HTTP 415.
- Business/domain rejection remains a 4xx response.
- Supabase connectivity, pool, cancellation and retryable transaction failures are treated as temporary infrastructure failure: HTTP 503 with `Retry-After`.
- Unknown Supabase failures fail safe as infrastructure failures instead of being presented as customer validation errors.
- If a canonical Tip is durably created but customer receipt-token retrieval temporarily fails, Tip creation remains successful and returns `receiptStatus: pending`; same-key replay remains protected by database idempotency.

Unit coverage exists in `src/lib/http-resilience.test.ts`.

### Database/application contract gate

`npm run db-contracts:check` scans application/server scripts for Supabase RPC names and verifies that those functions exist in repository migration history.

This guards against deploying application code that calls a database function absent from the schema history.

### Generated Supabase schema types

`src/types/database.ts` has been replaced with a fresh type generation from the canonical Supabase project after migration `mvp_v3_0047_admin_mfa_recovery_audit`.

Both server-side Supabase clients are now instantiated as `Database`-typed clients.

`npm run schema-types:check` requires the generated-type provenance migration number to equal the highest numbered repository migration. A later migration therefore forces regeneration before CI can pass.

### Migration safety

`npm run migration:safety` validates migration numbering and blocks high-risk destructive DDL (`DROP TABLE`, `DROP SCHEMA`, `TRUNCATE`, `DROP COLUMN`) unless an independently reviewed destructive-change marker is present.

The operational promotion procedure is documented in `docs/MIGRATION_DEPLOYMENT_GATE.md` and uses forward/additive migration, isolated-database testing and expand/migrate/contract principles rather than automatic destructive rollback.

### CI hardening

The canonical `npm run ci` chain now includes:

1. architecture check;
2. repository RPC contract check;
3. generated schema-type freshness check;
4. migration safety check;
5. TypeScript typecheck;
6. Vitest suite; and
7. Next.js production build.

GitHub Actions uses read-only repository permissions and cancels stale runs for the same branch/ref.
